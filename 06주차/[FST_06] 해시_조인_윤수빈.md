# 4장 조인 튜닝
## 4.3 해시조인
### 4.3.4 해시 조인 실행계획 제어
- use_hash 힌트 사용하여 제어
- leading 이나 ordered 힌트로 Build Input 또한 사용자가 직접 선택 가능
- swap_join_input으로 Build Input 명시적으로 선택 가능

- 세 개 이상 테이블 해시 조인
  /*+ leading(T1, T2, T3) use_hash(T2) use_hash(T3) */ *
  - 조인 순서에 맞게 위와같이 leading 힌트 지정
  - leading 힌트의 첫번때 파라미터 => Build Input
  - T1이 Build Input 으로 선택된 상황에서 T2를 Build Input 으로 선택하는 방법
    /*+ leading(T1, T2, T3) swap_join_inputs(T2) */ *
  - 조인한 결과집합을 (T1, T2) Build Input으로 선택하고 싶을 때
    /*+ leading(T1, T2, T3) no_swap_join_inputs(T3) */ *
### 4.3.5 조인 메소드 선택 기준
1. 소량 데이터 조인 -> NL 조인
2. 대량 데이터 조인 -> 해시 조인
3. 대량 데이터 조인인데, 해시 조인으로 처리할 수 없을 때, 즉 조인 조건식이 등치 조건이 아닐 때 -> 소트 머지 조인

- NL 조인 기준으로 최적화했는데도 랜덤 액세스가 많아 만족할만한 성능을 낼 수 없다면 -> 대량 데이터 조인에 해당

수행빈도가 매우 높은 쿼리의 경우 기준
1. NL 조인과 해시 조인 성능이 같으면, NL 조인
2. 해시 조인이 약간 더 빨라도 NL 조인
3. NL 조인보다 해시 조인이 매우 빠른 경우, 해시 조인

해시 조인은 아래 세 가지 조건을 만족하는 SQL 문에 주로 쓰임
1. 수행 빈도가 낮고
2. 쿼리 수행 시간이 오래 걸리는
3. 대량 데이터 조인할 때
=> 배치 프로그램, DW, OLAP성 쿼리 특징
## 4.4 서브쿼리 조인
### 4.4.1 서브쿼리 변환이 필요한 이유
- 서브쿼리 : 하나의 SQL문 안에 괄호로 묶은 별도의 쿼리 블록을 일컫음
- 서브쿼리 분류
  - 인라인 뷰 : FROM 절에 사용한 서브쿼리
  - 중첩된 서브쿼리 : WHERE 절에 사용한 서브쿼리
  - 스칼라 서브쿼리 : 한 레코드당 하나의 값을 반환하는 서브쿼리, 주로 SELECT-LIST에서 사용
- 옵티마이저는 쿼리 블록 단위로 최적화 수행
### 4.4.2 서브쿼리와 조인
- 필터 오퍼레이션
  - no_unnest : 서브쿼리를 풀어내지말고 그대로 수행하라는 힌트
  - NL 조인과의 차이점 
    1. 필터는 메인쿼리의 한 로우가 서브쿼리의 한 로우와 조인에 성공하는 순간 진행을 멈추고, 메인쿼리의 다음 로우를 계속 처리한다는 점
    2. 필터는 캐싱기능을 갖는다는 점
    3. 필터 서브쿼리는 메인쿼리에 종속되므로 조인 순서가 고정됨
- 서브쿼리 Unnesting
  - 메인과 서브쿼리 간의 계층구조를 풀어 서로 같은 레벨로 만들어 줌 => 일반 조인문처럼 다양한 최적화 기법 활용 가능
- 서브쿼리 Pushing
  - Unnesting 되지 않은 서브쿼리는 항상 필터 방식으로 처리됨 => 실행계획 상 맨 마지막 단계
  - Pushing 서브쿼리 : 서브쿼리 필터링을 가능한 한 앞 단계에서 처리하도록 강제하는 기능, push_subq/ no_push_subq 힌트로 제어
  - 이 기능은 Unnesting 되지 않은 서브쿼리에만 작동
  - push_subq 힌트는 항상 no_unnest 힌트와 동반 기술
